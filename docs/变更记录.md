# 变更记录

记录每一轮**试用/测试体验**提出的变更，以及它对应的规格、代码与测试改动，
保证"谁在什么时候因为什么改了哪里"可追溯。

变更流程（本项目约定）：

```
试用体验提出 → 判定是"规格缺口"还是"实现缺陷"
    ├─ 规格缺口：先改 规格说明.md → 再改 实现 → 再补测试
    └─ 实现缺陷：直接改实现 → 补回归测试 → 必要时补规格说明
→ 涉及界面/交互的，同步更新 docs/UI-UX-设计规范.md
→ 在本文件追加一条记录
```

## 第 4 轮（试用体验反馈）

来源：项目负责人在本机试用后提出 4 条反馈。

### CH-009 考生管理的场次选择改为「查询 + 可点击列表」

| 项 | 内容 |
|---|---|
| 原始反馈 | "考生管理关联考试场次的时候，如果场次很多，下拉框不好选，参考考试管理的查询" |
| 判定 | **可用性缺陷**（下拉框承载不了"多场次 + 需要看状态/时间"的场景） |
| 结论 | 换成查询条件 + 可点击结果列表；选中后收起为"已选 + 更换场次" |
| 规格改动 | `规格说明.md` 5.2「考生管理」 |
| UI/UX 改动 | `UI-UX-设计规范.md` §3.9「关联对象的选择（场次选择器）」——上升为通用规范 |
| 前端改动 | `CandidatesView.vue` 选择器重写；条件与「考试管理」完全一致 |
| 后端改动 | 无（复用 `GET /api/admin/exams` 的查询参数） |
| 测试 | `CandidatesView.spec.ts`「场次查询与选择」7 项 + E2E 更换场次流程 |

**为什么不简单地给下拉框加个搜索框**：下拉框即使能搜，也只能显示一行文本，
管理员仍看不到"这场是草稿还是进行中、什么时候开考"，而这两个信息恰恰决定
"我现在能不能导名单"。表格化结果列表顺手解决了这个问题。

### CH-010 考生管理提供参与状态查询

| 项 | 内容 |
|---|---|
| 原始反馈 | "考生管理除了导入信息，生成邀请码之外，提供状态查询功能，看谁在考试，谁没来" |
| 判定 | **功能缺口** |
| 结论 | 名单带参与状态：未登录 / 答题中 / 已交卷 / 超时交卷，并提供带人数的状态筛选 |
| 规格改动 | `规格说明.md` 5.2「考生管理」新增状态表、4.6 新增验收项 |
| UI/UX 改动 | `UI-UX-设计规范.md` §3.7 |
| 后端改动 | `GET /api/admin/exams/{id}/candidates` 的每行新增 `status` / `started_at` / `submitted_at` / `score` |
| 前端改动 | `CandidatesView.vue` 状态标签组、状态列、得分与交卷时间列；`lib/participation.ts`（新增） |
| 测试 | `test_candidate_status.py`（8 项）、`participation.spec.ts`（10 项）、`CandidatesView.spec.ts`（6 项） |

**关键区分**：以往"缺考"把"没登录"和"登录了但没交卷"混为一谈。
考试进行中时这两者含义完全相反——前者要催，后者是正常的。
所以状态里必须有独立的「答题中」。

**状态人数基于全量名单统计**，不随当前筛选变化，否则筛了"已交卷"之后
"未登录 0 人"会自相矛盾。这条已写进 UI/UX 规范并加了回归测试。

### CH-011 题库导出 CSV

| 项 | 内容 |
|---|---|
| 原始反馈 | "题库支持导出功能，csv 格式" |
| 判定 | **功能缺口** |
| 结论 | 新增 `GET /api/admin/questions/export`，列定义见规格 7.4 |
| 规格改动 | `规格说明.md` 5.2「题库管理」、4.11、新增 7.4 列定义 |
| 后端改动 | `services.export_questions_csv`；选项列按本次导出的最大选项数动态展开（最少 4 列） |
| 前端改动 | `QuestionsView.vue` 增加「导出题库 CSV」按钮 |
| 测试 | `test_question_export.py`（10 项）、`QuestionStats.spec.ts`（2 项） |

**设计取舍**：选项列**动态展开**而不是固定 4 列。管理员可能配 6 个选项，
固定 4 列会静默丢数据；动态展开既无损又不至于每次都摊出 8 个空列。

**统计列留空而非填 0**：与 CH-008 同一原则——"从未考过"不是"正确率 0%"。

**导入仍用 JSON**：CSV 面向人工阅读/备份，不承诺可回灌（回灌会引入
"选项列怎么映射回 key""多选答案分隔符"等一堆歧义）。导出里的 `ID` 列
特意保留，是为了让 JSON 重新导入时能按 `id` upsert。

### CH-012 生成《题库模板.md》

| 项 | 内容 |
|---|---|
| 原始反馈 | "生成一个题库模板.md，方便我测试的时候让 ai 再生成一批题目" |
| 判定 | **交付物缺口** |
| 结论 | 新增 `docs/题库模板.md`：给 AI 的指令模板、JSON 格式、字段约束、判分规则说明、自检清单、空白骨架 |
| 规格改动 | 无（属于辅助文档，非系统行为） |
| 代码改动 | 无 |
| 测试 | 无自动化测试；模板中的 JSON 示例与后端导入格式一致，由既有导入测试（`test_admin_tags.py` 等）间接保证格式正确 |

**为什么把判分规则也写进模板**：出题质量受判分规则影响很大。
多选"选错即 0 分"，意味着错误选项必须明显错误；若正确项多达 5~6 个，
漏选得分会很零碎，区分度反而下降。把规则写给 AI 看，比事后返工便宜。

## 第 3 轮（试用体验反馈）

来源：项目负责人在本机试用后提出 3 条反馈。

### CH-006 考试管理新增查询功能

| 项 | 内容 |
|---|---|
| 原始反馈 | "考试管理应该增加查询功能，考试多了之后，支持按状态、选聘编号、开考时间、名称（模糊查询）查询列表" |
| 判定 | **功能缺口**（原实现只有全量列表） |
| 结论 | 列表支持按状态 / 选聘编号（包含）/ 名称（模糊）/ 开考时间区间（起止）查询，条件可组合 |
| 规格改动 | `规格说明.md` 5.2「考试管理」新增查询要求、4.9 新增验收标准 |
| UI/UX 改动 | `UI-UX-设计规范.md` §3.6 查询表单规范 |
| 后端改动 | `GET /api/admin/exams` 增加 `status` / `recruitment_no` / `title` / `start_from` / `start_to` 参数；未知状态返回 422；空串视为不过滤 |
| 前端改动 | `ExamsView.vue` 查询条件栏、空态区分"无数据/无结果"、条件同步地址栏 |
| 测试 | `backend/tests/test_exam_query.py`（10 项）、`frontend/tests/ExamQuery.spec.ts`（11 项） |

**设计取舍**：`status` 采用**对外状态**（草稿/未开始/进行中/已结束/已归档）而不是数据库里的
`draft/published/archived`，因为管理员在界面上看到的就是前者；两者不一致会让查询结果"对不上号"。
由于对外状态是惰性计算的，过滤在内存完成（考试数量级很小）。
开考时间用**本地日期区间**，前端换算成 UTC 时刻再下发——否则东八区会整体偏 8 小时。

### CH-007 新增「考生管理」模块

| 项 | 内容 |
|---|---|
| 原始反馈 | "管理端新增考生管理模块，考试管理模块中，列表项的「名单/成绩」按钮，在发布前的功能在考生管理模块实现，通过下列查询选择要导入候考/生成邀请码的考生所属的考试场次" |
| 判定 | **规格缺口 + 信息架构缺陷**（功能存在但摆放位置不符合管理员心智模型） |
| 结论 | 把**发布前**的名单与邀请码操作迁到独立的「考生管理」模块，通过考试场次选择器指定目标场次 |
| 规格改动 | `规格说明.md` 5.2 新增「考生管理」功能段与「导航结构」表、4.6 补充入口位置 |
| UI/UX 改动 | `UI-UX-设计规范.md` §3.1 导航结构 + 职责边界表 |
| 前端改动 | 新增 `CandidatesView.vue`；`ExamDetailView.vue` 移除名单面板，只保留成绩与统计；`ExamsView.vue` 操作列按状态重组，草稿行提供「名单与邀请码」跳转（带 `?exam=<id>` 预选） |
| 后端改动 | 无（复用既有名单与邀请码接口） |
| 测试 | `frontend/tests/CandidatesView.spec.ts`（14 项）、`ExamQuery.spec.ts` 中的操作列与跳转断言（4 项） |

**为什么不做全局考生库**：名单的本质是"某场考试的考生"（`exam_candidates`），
而考生主数据（`users`）本来就是全局复用的——同一人参加多场考试时档案自动复用。
在没有"跨场次批量操作"的真实需求前，引入全局考生库只会多一层概念。
真正的痛点（找不到导入入口、要选场次）用"顶级模块 + 场次选择器"就解决了。

**二次确认保留**：重新生成邀请码仍必须二次确认，且确认文案里写明"旧码立即失效"。

### CH-008 题库管理新增题目统计

| 项 | 内容 |
|---|---|
| 原始反馈 | "题库管理新增统计功能，能看到每个题目上次被随机抽中的考试名称和时间，累计答题正确率" |
| 判定 | **功能缺口** |
| 结论 | 题库列表展示每题「上次被抽中的考试名称与时间」与「累计答题正确率」 |
| 口径确认 | 累计正确率**含未作答**：正确次数 ÷ 所有已判分提交次数，与"标错率"互补（相加为 100%） |
| 规格改动 | `规格说明.md` 5.2「题库管理」新增统计要求、4.10 新增验收标准 |
| UI/UX 改动 | `UI-UX-设计规范.md` §3.7 统计展示规范 |
| 后端改动 | 题库列表返回 `stats`：`last_drawn_exam_title/at`、`answer_count`、`correct_count`、`correct_rate` |
| 前端改动 | `QuestionsView.vue` 新增「上次被抽中」「累计正确率」两列 |
| 测试 | `backend/tests/test_question_stats.py`（8 项）、`frontend/tests/QuestionStats.spec.ts`（7 项） |

**两个刻意的设计点**：

1. **"暂无" ≠ "0%"**：从未被抽中、或从未被作答时返回 `null`，界面显示「暂无」。
   若一律显示 0%，管理员会把"还没考过"误读成"所有人都做错"，进而误判题目难度。
2. **百分比必须带样本量**：显示 `75%（6/8）`。只有百分比时，2/2 与 200/200 看起来一样可信。

**跨场次累计**：正确率统计所有已判分提交（不限某一场考试），
因此它是"这道题一直以来的表现"；单场表现请查该场考试统计里的"标错率"。

### CH-001 选项标号按显示位置重排为 A、B、C、D

### CH-003 管理端「考生管理」模块 —— 本轮不改，待下轮体验

| 项 | 内容 |
|---|---|
| 原始反馈 | "管理端应该有考生管理模块，没有导入学生信息的入口" |
| 判定 | **待澄清**（导入入口其实存在，但不在顶级导航里，管理员没找到） |
| 本轮结论 | 按项目负责人意见**本轮不做**，等下一轮体验后再决定是否提升为顶级模块 |
| 规格改动 | 无 |
| 代码改动 | 无 |

**当前导入入口的实际位置（供下一轮体验时验证）**：

```
管理端 → 考试管理 → 该场考试行末「名单/成绩」→ 名单与邀请码 → 导入考生名单
```

之所以放在考试详情内，是因为**名单是"按场次"的**：CSV 导入会把考生关联到
**这一场考试**（`exam_candidates`），而考生主数据（`users`）是全局复用的。
菜单级的"考生管理"若要与现有数据模型自洽，需要先确定三选一的定位：

1. 全局考生库（列表 + 全局导入 + 查看每人参加了哪些考试），入场关联仍在考试详情；
2. 全局库 + 支持从库中勾选考生加入某场考试；
3. 不做全局库，只把"按考试导入"的入口在考试列表行内直接暴露出来。

选项 1 / 2 需要新增后端接口；选项 3 纯前端改动，成本最低。

### CH-005 组卷规则标签改为封闭选项

| 项 | 内容 |
|---|---|

从根上避免了"组卷规则里有一个题库中不存在的标签"这种必然失败的配置。
