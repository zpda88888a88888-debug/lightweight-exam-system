## 2. 与数据模型的有意偏差

### 2.1 `exam_candidates.invite_code` 允许为空

- 架构 6 数据模型标注 `invite_code TEXT NOT NULL UNIQUE`。
- 但测试方案 6.8 要求「名单导入后未生成邀请码时，考生无法登录」，
  6.9 也把「导入」与「生成邀请码」列为两个独立步骤。

**结论：改为 nullable + UNIQUE。** SQLite 的 UNIQUE 允许多个 `NULL`，
因此既满足「生成前为空」，又保持「码全局唯一」。

- 实现：`app/models.py::ExamCandidate`
- 测试：`tests/test_invite_codes.py::test_login_fails_before_codes_generated`

### 2.2 发布快照采用引用式，因此题库侧需要冻结守卫

- 架构 6 的 `exam_questions` 只存 `(exam_id, question_id, seq, score)`，即**引用式快照**，
  不冗余题干/选项/答案。
- 架构 9.6 又要求「之后修改题库不影响已发布考试」。

单纯按数据模型实现会导致：改动或删除题库题目，会**穿透影响已发布考试的试卷**
（题干被改、题目消失）。为同时满足两者，在题库侧增加守卫：

**已被「非草稿」考试引用的题目，禁止修改与删除（409）。**

- 实现：`app/routers/admin.py::_ensure_question_mutable`
- 测试：`tests/test_publish_freeze.py::test_used_question_cannot_be_edited_after_publish`、
  `::test_used_question_cannot_be_deleted_after_publish`、
  `::test_unused_question_can_still_be_edited_and_deleted`、
  `::test_draft_exam_referenced_question_free_to_edit`

> 这保证了「发布即冻结」的口径延伸到题目内容，且不误伤题库中未被引用的题目。
> 若将来需要允许修改已引用题目，必须先把快照改成内容冗余式（在 `exam_questions`
> 中冗余题干、选项、答案、解析），那是数据迁移级别的变更。

### 2.3 「组卷规则非空」为发布前置条件

架构与规格都未明说组卷规则为空时的行为。实现在发布时拒绝空规则（400），
避免产生一份 0 题的考试。

- 实现：`app/services.py::publish_exam`
- 测试：`tests/test_publish_freeze.py::test_publish_without_rules_rejected`

## 3. 统计口径的精确定义

规格多次使用「所有有 attempt 的人」作为分母。实现中进一步明确：

> **「有 attempt 的人」= 已产生判分结果的 attempt**
> （`status` 为 `submitted` 或 `timeout_submitted`）。

- 从**未交卷**（`in_progress`）的 attempt **不计入**平均分 / 及格率 / 标错率的分母。
- 这类人在成绩导出中状态显示为**缺考**，得分为空；但 `开始时间` 会保留其真实开始时间。

理由：交卷前没有分数，把未交卷者按 0 分计入会系统性拉低平均分与及格率；
而规格 7.3 的状态列只有「正常提交 / 超时提交 / 缺考」三种取值，未交卷只能归入缺考。

- 实现：`app/services.py::_finalized_attempts`
- 测试：`tests/test_stats_export.py::test_average_score_denominator_excludes_absent`、
  `::test_stats_on_exam_without_attempts`

> 正常部署下影响很小：前端在 `end_at` 会自动交卷，未交卷只出现在考生直接关掉页面的场合。

## 4. 并发与数据库

### 4.1 连接池使用 NullPool（性能关键）

SQLAlchemy 默认 `QueuePool` 只有 **5 + 10 = 15** 条连接。
200 并发交卷时，请求会在**取连接阶段**直接超时失败：

```
TimeoutError: QueuePool limit of size 5 overflow 10 reached
```

这由 200 并发压测实测暴露（当时 200 个请求中 156 个失败，耗时 124 秒）。

SQLite 本身把写入串行化，连接池限流并不能提升吞吐，只会把「排队」变成「失败」。
改用 `NullPool`（每请求一条短连接）后，200 并发全部成功，耗时降到 6 秒。

- 实现：`app/db.py::create_db_engine`
- 测试：`tests/test_concurrency.py::test_200_concurrent_submissions_no_data_loss`

### 4.2 交卷幂等的双重保障

`submit_attempt` 采用：

1. **进程内按 `attempt_id` 加锁**——同一 attempt 的并发提交串行化。
2. **锁内 `session.rollback()` + 重新读取**——关键点：WAL 模式下，请求进入时开启的
   读事务会固定在旧快照上，若不重新开启事务，就**读不到前一个并发请求刚提交的终态**，
   从而导致重复判分（此 bug 由并发测试捕获）。
3. **条件更新认领**——`UPDATE attempts SET ... WHERE id=? AND status='in_progress'`，
   仅当 `rowcount == 1` 时本次判分生效；否则回滚已写入的 answers 并返回既有结果。
   这是跨进程兜底。

- 实现：`app/services.py::submit_attempt` / `_finalize_attempt`
- 测试：`tests/test_attempt_idempotency.py::test_concurrent_same_attempt_submit_judges_once`、
  `tests/test_concurrency.py::test_concurrent_submissions_are_idempotent_under_load`

> **多进程部署注意**：第 1 条是进程内的。若日后用 `uvicorn --workers N` 或多实例，
> 第 3 条条件更新仍能保证不重复判分，但落败请求会拿到既有结果而非阻塞等待，
> 属于可接受行为。真正需要横向扩展时，按架构 13 升级到 PostgreSQL。

### 4.3 备份与 WAL

备份用 `sqlite3` 的在线备份 API，WAL 模式下无需停服即可得到一致快照。

- 实现：`app/backup.py`
- 测试：`tests/test_backup.py`（10 项，含恢复演练与保留策略）

## 5. HTTP 语义约定

| 场景 | 状态码 | 选择理由 |
|---|---|---|
| 时间窗口不满足、已交卷、冻结冲突 | **409 Conflict** | 都是「资源当前状态不允许该操作」，且 spec 4.1 明确要求已交卷返回 409 |
| 凭证不匹配（手机号/邀请码/密码） | **403** | 请求本身合法，但无权访问 |
| 缺少/伪造/过期 token | **401** | 未认证 |
| 角色不匹配（管理员 token 访问考生端） | **403** | 已认证但权限不足 |
| 参数/表头/校验失败 | **422** | FastAPI 与 Pydantic 的默认语义 |
| 组卷规则为空 | **400** | 请求内容本身不成立 |

## 6. 其他实现取舍

| 项 | 决策 | 理由 |
|---|---|---|
| token 实现 | 标准库 HMAC-SHA256 自签，不引入 JWT 库 | 减少依赖面；无状态、可校验过期 |
| 时间类型 | 统一 naive UTC | 规避 SQLite 时区歧义；所有比较都在服务端完成 |
| 时钟 | 一律通过注入的 `Clock` 取时间 | 满足测试方案风险 R5「禁止 `datetime.now()` 出现在被测逻辑」 |
| 成绩 CSV 编码 | UTF-8 无 BOM，行尾 CRLF | BOM 会污染列头断言；CRLF 兼容 Excel |
| 缺考的「是否及格」列 | 空字符串 | 无分数即无及格判定，避免误导 |
| 切换屏时间点列 | JSON 数组序列化 | spec 7.3 允许「可读字符串或 JSON」；JSON 可无歧义还原 |
| 同一题命中多个标签规则 | 不重复入卷 | 避免试卷出现重复题目 |
| 多标签交叉 | 抽题时排除已选题目 | 同上 |
| 判分配置错误 | 该题记 0 分，不阻断交卷 | 考生不应为管理员的题目配置错误而无法交卷 |

## 7. 前端决策

### 7.1 路由使用 hash 模式

管理端是独立入口 `admin.html`，与考生端 `index.html` 并列。
若用 history 模式，刷新 `/exams` 这类路径时静态服务器会回退到 `index.html`
（即**考生端**），管理端页面直接丢失；要修好就得为每个入口配置 rewrite。

改用 `createWebHashHistory()` 后，`dist/` 是纯静态文件，**任意刷新都不会 404，
不需要任何服务器 rewrite 配置**，与「极轻量级、nginx 直接托管静态文件」的定位一致。

### 7.2 答案不做防抖，每次选择立即写 IndexedDB

最初实现是 200ms 防抖保存。浏览器 E2E 复现了问题：
**作答后立即刷新 → 防抖定时器被页面卸载打断 → 答案丢失**。
这直接违反 spec 4.2「答案实时保存在本地，刷新页面后答案不丢失」。

一次 IndexedDB 写入开销极小（单次考试最多几百次选择），
因此改为每次变更立即写入，彻底消除这个丢数据窗口。

- 测试：`frontend/tests/ExamView.spec.ts::选择答案后写入 IndexedDB`（50ms 内即落盘）

### 7.3 恢复答案用「内存优先」合并，而不是直接覆盖

`answerStore.load()` 是异步的。若考生在读取完成前就已作答，
直接 `session.answers = await load()` 会把这几秒内的作答覆盖掉。
改为 `session.answers = { ...stored, ...session.answers }`：
内存中的新作答优先，磁盘上的旧数据补齐其余题目。

### 7.4 刷新后自动重拉试卷

`session.questions` 不持久化（试卷体积大且服务端可重建），
只持久化 `token / exam / attemptId`。早期版本在 `/exam` 发现试卷为空就退回等待页，
导致刷新后需要重新点「开始考试」。现在 `ExamView` 在试卷为空时自动 `getPaper`：
题目顺序与选项乱序都由服务端按考生种子确定，因此重拉内容与刷新前完全一致。

同时 `WaitingView` 必须在拿到 attemptId 后立即 `persistSession()`，
否则刷新后守卫读不到 attempt，同样会退回等待页。

- 测试：E2E 中 `page.reload()` 后断言 `.option.is-selected` 仍为 1

### 7.5 题目表单自动丢弃「内容为空」的选项

表单默认给 4 个选项，但多数题目只有 2~3 个。
早期版本要求所有选项都填内容，否则报「选项内容不能为空」，
迫使管理员手动删空行（E2E 因此失败）。

改为提交时自动丢弃内容为空的选项；若被丢弃的选项恰好被勾为正确答案，
则明确报错要求改选，避免静默产出错误答案。

### 7.6 服务端时间一律按 UTC 解析

后端用 naive UTC 序列化（`"2026-09-19T11:00:00"`，无 `Z`）。
`new Date(...)` 会按**本地时区**解析，在东八区直接偏差 8 小时。
所有解析统一走 `parseServerTime`（无时区标记时补 `Z`）。

反向提交时（管理端 `datetime-local` 表单）必须去掉时区标记，
否则数据库会混入 aware datetime，与 `now()` 的 naive UTC 比较时出错。

- 测试：`frontend/tests/time.spec.ts`（含本地↔UTC 往返一致性）

### 7.7 切屏只在「变为隐藏」这一跳变时计数

`visibilitychange` 在隐藏与恢复时都会触发，且浏览器可能重复派发。
若不做跳变判断，一次切屏会被计成多次。
实现记录 `alreadyHidden` 状态，仅在 `hidden` 由 false 变 true 时计数 +1。

### 7.8 技术栈版本约束

- **TypeScript 固定在 5.x**：TS 7（原生端口）移除了 `./lib/tsc` 导出，
  `vue-tsc@3` 无法工作，会直接报 `ERR_PACKAGE_PATH_NOT_EXPORTED`。
- **Vite 8 开发服务器绑定 IPv6 localhost**：请用 `http://localhost:5173` 访问，
  用 `127.0.0.1` 连不上。已在 `frontend/README.md` 标注。

## 8. 离线部署（Linux ARM64）

目标环境：内网、无外网、不能装 npm/pip 依赖、无 Docker，但有 Node。
产物：`deploy/out/exam-system-<版本>-linux-arm64.tar.gz`（约 19 MB）。

### 8.1 依赖全部随包分发

服务器不能联网装依赖，因此在**开发机**上预先下载目标平台的 wheel：

```bash
pip download --only-binary=:all: \
  --platform manylinux2014_aarch64 --platform manylinux_2_17_aarch64 \
  --python-version 3.11 --implementation cp -r requirements-deploy.txt
```

依赖树里只有两个**原生二进制**包：`pydantic_core`、`sqlalchemy`，
它们必须与目标平台 ABI 匹配（macOS wheel 拿到 Linux 上无法加载）。
其余 13 个都是 `py3-none-any` 纯 Python。构建脚本会校验：

> 若 wheelhouse 中出现非 `manylinux.*aarch64` 且非 `none-any` 的 wheel → 直接构建失败。

因为服务器 Python 版本未知，包里同时带 3.10 / 3.11 / 3.12 三份（合计约 19 MB），
`install.sh` 在安装时按实际版本择一。

### 8.2 默认「解压 wheel」而不是 pip install

wheel 本质就是 zip，解压到 `backend/vendor/` + `PYTHONPATH` 即可运行，
**完全不需要 pip、不需要 venv**。

选它作为默认路径的原因：
- Ubuntu 24.04 默认不带 pip，且 PEP 668（externally-managed-environment）
  会拦截系统级安装，`python3 -m pip install` 很可能直接失败；
- 解压路径只依赖 python3 本身，任何发行版都能跑。

保留了 `./install.sh --use-pip` 走标准 pip 安装（`--no-index --find-links` 离线），
两条路都验证过。

### 8.3 用 uvicorn 而不是 uvicorn[standard]

`[standard]` 会带入 uvloop / httptools / watchfiles 三个需要编译的扩展，
在内网无编译环境下风险高。普通 uvicorn 只依赖纯 Python 的 h11，
性能对本场景（200 并发交卷已压测通过）完全够用。

### 8.4 用 Node 承担静态托管与反向代理，不装 Nginx

`server/server.js` 只用 Node 内置模块，实现：

- 托管前端产物（带 hash 的资源长缓存、html 不缓存）；
- 把 `/api/*` 反向代理到 `127.0.0.1:8000`；
- 防目录穿越；后端不可用时返回可读的 502 提示。

于是不需要 Nginx、不需要 npm install，也不会引入任何需要编译的 npm 包。
后端只监听 `127.0.0.1`，由 Node 统一对外，减少暴露面。

### 8.5 备份必须是「单文件」

架构 11 要求把备份文件复制到另一台机器或内网 NAS。
但 SQLite 备份默认**继承源库的 WAL 设置**，会在旁边生成 `-wal`/`-shm`，
此时只拷 `.db` 就会丢掉仍在 WAL 中的数据 —— 备份等于无效。

因此在 `create_backup` 中对备份库执行 `PRAGMA journal_mode=DELETE`，
产出真正自包含的单文件；`prune_backups` 也会一并清理历史遗留的附属文件。

- 实现：`backend/app/backup.py`
- 测试：`tests/test_backup.py::test_backup_is_self_contained_single_file`、
  `::test_prune_removes_wal_sidecars`

### 8.6 bash 多字节变量展开陷阱（部署包实战踩坑）

`install.sh` 首次在真实环境执行时报 `PYTHON�: unbound variable`，直接启动失败。
原因：脚本里写了 `"$PYTHON（..."`，某些 locale 下 bash 会把全角括号 `（`
的首字节并入变量名，于是变成了未定义变量。

修法：**所有紧跟多字节字符的变量一律写成 `${VAR}`**（本次修复 12 处）。
并在 `deploy/build.sh` 中加了构建期检查：扫描所有交付脚本，
发现 `$VAR` 紧跟非 ASCII 字符就**直接构建失败**，防止回归。

### 8.7 systemd（可选但推荐）

考试期间最怕进程挂掉，因此提供 `systemd/install-systemd.sh`，
注册 `exam-backend` 与 `exam-web` 两个服务，具备开机自启与崩溃自动拉起。
不用 systemd 时也可以通过 `./manage.sh start` 裸跑。

### 8.8 本机验证的边界（重要）

aarch64 的二进制扩展**无法在 macOS 开发机上执行**，因此这部分无法本地验证。
已做的替代验证：

| 验证项 | 方式 | 结果 |
|---|---|---|
| wheel 平台标签正确 | 构建期脚本校验 | ✅ 全部 `manylinux.*aarch64` 或 `none-any` |
| 解压安装机制可用 | 用 macOS wheel 走完全相同的 `install.sh` 流程 | ✅ 依赖导入成功 |
| 启动脚本 / 进程管理 | 在真实文件系统上跑 `doctor`/`start`/`status`/`backup`/`stop` | ✅ 全部通过 |
| Node 静态托管 + 代理 | 经 8080 访问页面与 `/api` | ✅ 200 / 转发正常 |
| 整体业务闭环 | 冒烟脚本经 Node 跑 34 项断言 | ✅ 全部通过 |
| 浏览器端真实可用 | Playwright 主干流程指向部署实例（`E2E_BASE_URL`） | ✅ 通过 |
| 依赖自检 | `install.sh` 与 `manage.sh doctor` 在目标机 import 校验 | 部署时兜底 |

部署时若 ABI 不匹配，`install.sh` 会在自检阶段就报错并提示，
不会出现「服务起来了但一用就崩」的情况。

## 9. 明确不做（与 spec 9 一致）

考生查分入口、发布成绩流程、设备锁、考试中答案保存接口、定时任务扫描考试状态、
Redis / MQ / 微服务 / K8s、图片音频题目。另按本轮约定不做部署编排（Docker / Nginx）。
